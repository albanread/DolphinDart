# Toolchain and build layout (DD0)

**Rule: nothing generated ever lives inside this repo.** The Dart 1.24.3
quarry, the extracted tree, and the build directories are all outside it — the
repo carries only owned source (`port-win/`, `port-arm64/`, `st/`, `test/`,
`tcl/`, `tools/`, `docs/`).

## Locations

| What | Where | Notes |
|---|---|---|
| Repo | `C:\projects\DolphinDart` | this checkout |
| **Work area** | `C:\projects\dolphindart-work` | generated: `tree/`, `build-arm64/`, `build-x64/` |
| Quarry (Dart 1.24.3 sources) | `C:\projects\WINDARTARM\sdk-1.24.3` | **read-only, shared** with the sibling WINDART port; extract never writes to it |
| Extracted tree | `C:\projects\dolphindart-work\tree` | generated by `extract.py`; **ours alone** — it carries this repo's patches |
| Builds | `C:\projects\dolphindart-work\build-{arm64,x64}` | Ninja + MSVC |

**Why a separate work area (DD0 change).** The seed assumed the repo sat
*inside* its work area (`<workroot>\WINDARTTALK`), so `extract.py` and
`build.ps1` derived the workroot as the repo's parent's parent. Cloned at
`C:\projects\DolphinDart` that resolves to `C:\projects`, which would scatter
`tree/` and `build-*/` across the projects root **and share a tree with the
WINDART port** — whose patches will diverge from ours the moment DD4/DD6 touch
the front-end. Both scripts now take an explicit workroot:

- `extract.py`: env `WINDART_WORKROOT` (also `WINDART_SDK_SRC`, `WINDART_TREE`)
- `build.ps1`: `-WorkRoot` parameter, falling back to env `WINDART_WORKROOT`,
  falling back to the old repo-relative behavior

## Commands

Extract (idempotent; re-run after changing any `port-*/**.patch`):

```bash
WINDART_WORKROOT=C:\projects\dolphindart-work WINDART_SDK_SRC=C:\projects\WINDARTARM\sdk-1.24.3 python port-win\extract.py
```

Build (PowerShell — `build.ps1` drives MSVC through vcvars; it will not work
from bash):

```bash
powershell -ExecutionPolicy Bypass -File port-win\build.ps1 -Arch arm64 -WorkRoot C:\projects\dolphindart-work -Tree C:\projects\dolphindart-work\tree
```

`-Arch x64` builds the x64 control (native arm64 cross-tools, runs under WoA
emulation). `-Clean` wipes the arch's build dir first. Output and full log:
`<workarea>\build-<arch>\{dart.exe,build.log}`.

Headless world boot + functional checks:

```bash
C:\projects\dolphindart-work\build-arm64\dart.exe test\st_world_run.dart st\world
```

## Requirements (verified on this host, 2026-08-15)

- **Visual Studio 18 Professional** at `C:\Program Files\Microsoft Visual Studio\18\Professional` (build.ps1 pins this path; CMake and Ninja are taken from the VS-bundled copies, not PATH).
- **Python 3.12 arm64** at `%LOCALAPPDATA%\Programs\Python\Python312-arm64\python.exe`. The `python3` on PATH is a Microsoft Store alias stub — it is not Python and will fail.
- Host: Windows 11 on ARM64. `arm64` is the primary target; `x64` builds with arm64 cross-tools and runs emulated, which is what makes it a useful control.

## Verifying what you built

Never infer architecture from a path or a directory name — read the PE header:

```bash
powershell -Command "$b=[IO.File]::ReadAllBytes('C:\projects\dolphindart-work\build-arm64\dart.exe'); $p=[BitConverter]::ToInt32($b,60); '{0:X4}' -f [BitConverter]::ToUInt16($b,$p+4)"
```

`AA64` = ARM64, `8664` = x64.
