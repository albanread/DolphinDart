How to read these drawings

The fills carry the project's own doctrine: what belongs to Dolphin gets ported, what sits underneath it may be written in whatever language fits, and every stand-in must name the thing that will retire it.

Dolphin's own Smalltalk
Translated D8 source, unmodified in meaning. This is the deliverable — never re-implemented in Dart or C++.
Machinery underneath
C++ or Dart, chosen per job: the compiler, the wndproc door, the FFI floor, the worker transport, the tooling.
Stand-in, retirement named
Hand-written compat Smalltalk that duplicates a translated class's role. Allowed only while the thing that kills it is written down.

Figure 1 — Source to machine code

Two crossings, and an interpreter in neither of them

Dolphin's .cls and .pax chunk files are translated into the house dialect ahead of time, by Python. From there a C++ front end living inside the VM takes them the rest of the way: no image file, no bytecode set, no dispatch loop — just flow-graph IR handed to a JIT that shipped in production in 2017.

Figure 2 — The object model is fused

A Smalltalk object is a Dart object; a send resolves four ways

The pipeline above compiles user-written methods, but it is not the whole runtime. The core classes are not ported — they are identified with Dart's own: a SmallInteger is a Dart int, an Array is a Dart List, a String literal is a Dart String. Nothing is boxed or wrapped, so the JIT optimizes them as the native types they already are. The cost of that fusion is dispatch: a single Smalltalk send can be answered in four different places, and only two of them are Smalltalk.

These are sealed Dart core classes — the VM will not let Smalltalk subclass them — so each carries a parallel "<Name> ext" holder where its Smalltalk-only methods live, reached only once ①, ② and ③ have all missed. The same machinery explains the house failure mode: an unbound capitalized name is not an error but a nil-valued static field minted on STGlobals, so a missing global surfaces as doesNotUnderstand on nil, far from its cause.

Smalltalk's control machinery is Dart's, too

The entanglement is not only the object model. The exception hierarchy is ordinary prelude source, but its verbs are primitives that lower straight onto Dart's own runtime — which is why non-local return and ensure: unwinding are exact rather than approximated.

on:do: / ensure:

  • stOnDo compiles to a Dart try / catch; ensure: and ifCurtailed: to try / finally.
  • A non-local return rides Dart's unwinding with a per-activation NLR home token, so an ensure: block fires mid-unwind exactly as ANSI requires.

signal / raise

  • signal is a <stprim> that becomes a Dart throw.
  • A native Dart error is reified the other way: a division by zero caught by stOnDo is handed back as a Smalltalk ZeroDivide, any other as a plain Error.

become:

  • Not re-implemented — it is the VM's own Become::ElementsForwardIdentity, the same primitive that powers hot-reload.
  • Exposed to the image through STSystem. It is the one feature the sibling macOS port had to drop.

Figure 3 — What the running image stands on

The seam is a wndproc, and it re-enters

Win32 sends are synchronous, so a Smalltalk handler that calls CreateWindowExW re-enters the image from inside its own call, to arbitrary depth. Everything about the floor's shape follows from surviving that: the door holds no Dart handle across an invoke, and continuations are posted to a queue drained outside the current entry rather than called back directly.

The scope rule, four ways

Every architectural argument on this project resolves to one question: does this belong to Dolphin, or is it machinery underneath Dolphin?

Ported, unmodified

  • The MVP framework — Model-View-Presenter and the class browsers, in Dolphin's own Smalltalk. This is the goal gate, not a milestone on the way to one.
  • The dialect semantics and the Windows primitives the framework needs.
  • MVP in the corpus is byte-identical to upstream D8, so what ships here is verifiably Dolphin's.

Ours to write

  • The compiler — front end to Dart flow-graph IR, in C++ inside the VM.
  • The door and the pump, the FFI floor, the struct generator.
  • Workers on isolates in place of green processes. Dart is a substrate with exactly the standing C++ has here — never a second home for application logic.

Linked, not re-typed

  • Scintilla and Lexilla, rebuilt ARM64. Dolphin already drives them through 438 KB of Smalltalk we keep.
  • DolphinDR8.dll — the artwork loads through Dolphin's own resource path, from a DLL rebuilt for this architecture under the original name.

Never ported

  • Dolphin's 386 bytecode interpreter. The execution model is fixed: front end → Dart IR → JIT. There is no interpreter to port to.
  • The dsfork VM. It does not work. It is never an oracle and never a dependency — only reading material for semantics.
  • A green-thread scheduler. This VM has none and will not grow one.

Four traps that shaped the architecture

Each of these is a class of silent failure, and each one is why a piece of the tooling in Figure 1 exists at all. None of them raise.

01

Dolphin is a 32-bit system, so every byte number in the corpus is suspect. A wrong offset reads the neighbouring field and the code keeps running. One literal — nmNotify: reading the code at 8 instead of 16 — silently disabled every WM_NOTIFY handler in the port. Struct sizes now come from winkb's types.size_bits rather than arithmetic; 90 were wrong, and correcting them uncovered five latent gate failures that were all one bug.

02

A method named after a universal helper may be dead on arrival. The IL builder rewrites 51 selectors at the call site, so a send under one of those names never reaches Smalltalk lookup. Object>>value written in Smalltalk blew the stack on every gate; ExternalMemory>>asInteger did nothing at all. Fixes belong in the helper's slow path, by protocol probe.

03

Silent nil is the house failure mode. An unbound global is nil. A class-side method on a bridged core name may be unreachable. initialize is never called by a file-in loader unless emitted as a top-level statement. Each presents far from its cause, usually as doesNotUnderstand on nil inside a contained handler — and handler errors are contained twice, by the image and again by the door.

04

Assertions cannot see pixels. listItemCount answered 33 while zero rows drew. Handles, class names and counts all pass on an invisible failure, so any change meant to affect what draws is not done until a screenshot shows it: Win32 mvpCapture:path:clientOnly: from a real message loop, converted by tools/shot.py, and read.
